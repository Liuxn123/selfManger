# 全项目性能诊断与优化方案

日期：2026-10-19；任务：T-109。

## 结论

当前卡顿有三条已复现的主要路径：模块切换触发跨页面重复刷新；项目读取反复校验整张登记表；知识库长写事务阻塞 UI 线程写任务记录。长项目文档的主线程解析会进一步放大停顿。

建议先切断刷新放大和读写互锁，再优化项目快照与按需渲染。暂不需要换界面框架、换数据库或扩大线程池。

本轮只增加诊断脚本、测量结果和方案，未修改业务代码、真实数据库、Vault、凭据或已运行客户端。仓库原有大量未提交修改保持原状。性能结论针对当前工作区源码；未确认用户此前使用的可执行包与这份源码完全一致。

## 测量范围与方法

- 审查六个现行模块的导航、启动、数据加载、刷新回调、项目详情、知识扫描、任务与口令设置链路；检查 SQLite 访问和线程池调度。
- 使用项目 `.venv/Scripts/python.exe`、PySide6 离屏窗口，生成 14 个虚构项目，不连接真实项目工作区。口令读取 mock 为 None，不访问系统凭据。
- 导航顺序为计划→项目→知识库→数据安全→设置→工作台，执行两轮，共 12 次切换。每次等待任务、线程池和主要刷新定时器稳定；观测额外等待 400 ms 的安静窗口，结果扣除该等待。
- `dispatch_ms` 只表示调用切换动作的同步耗时；`settle_ms_excluding_400ms_quiet` 表示切换后后台与主要回调稳定耗时，包含当前实现的防抖等待，并非“窗口完全冻结时间”。
- 10 ms QTimer 测界面心跳间隔；cProfile 辅助定位。计数器与 profiler 有开销；下面是单机小样本诊断值，不是正式 P95 或真实客户端帧率。
- 文件扫描另用 200 份不变的虚构 Markdown；长文档场景使用每份 348,086 字节、1,200 条日期段落的虚构 HANDOFF。

这里的“屏蔽”只是在探针进程中 monkeypatch `window.import_legacy_tasks`，不改产品代码；启动迁移仍执行。它证明重复刷新是重要原因，也表明单修此项不能解决项目页问题。后台任务减少约 74%，UI 数据库连接减少约 70%。两组样本存在冷热缓存差异，不能直接作为产品最终提速承诺。

知识库独立测量：

- 首次扫描 200 文件约 2,843 ms；文件完全未改时第二次仍约 3,021 ms。
- 两轮都重新读取 200 份正文、执行 200 次 `INSERT OR REPLACE`、202 次 SELECT；未使用文件时间/大小跳过不变正文与写入。
- 在第二个文件读取处人为加入 500 ms 延迟、确保扫描已开始写事务后，从主线程调用与导航相同的 `store.start_task()`，实际阻塞 2,243 ms。等待包括剩余扫描时间，不能全部归因于人为延迟。该实验直接复现写锁等待；真实库中的发生频率尚未测量。
- 扫描结果均 200 项、0 错误。

长文档场景在已经屏蔽导航导入的前提下，项目 `render()` 最大 326 ms，导航阶段最大心跳间隔 339 ms。profile 指向 `overview_snapshot → sections/outside_fences` 等正文解析；本场景的单次 `setMarkdown` 很短，因此不能把此项简单归结为 Markdown 排版慢。

## 原因与改法

### 1. 模块切换重复触发迁移和跨页刷新（P1，已复现）

代码：`ui/window.py:1355 page_changed`、`:1378 import_legacy_tasks`、`task_migration.py:migrate_legacy_tasks`。

```text
切到工作台 / 计划 / 项目
  → import_legacy_tasks
  → migrate_legacy_tasks + import_legacy_plans
  → imported 回调
  → 工作台.refresh + 计划.refresh + 项目.refresh
  → 项目列表完成后再读项目详情
```

切到计划、项目时，`page_changed` 还会直接调用目标页 refresh。`pending_refresh` 只能把同时到来的请求合并成下一轮，并不消除无变化的重复读取。日记录迁移函数末尾还会在无新增时 `set_setting` 写回标记。个人计划迁移自身有一次性标记，因此不是每次都重导全部旧计划；问题在于检查仍被调度，且无变化也刷新三页。

改法：

1. 启动按配置版本做一次兼容检查；日期目录出现新文件、导入来源变化或显式“重新导入”时才再执行。保留增量导入能力。
2. 导入报告返回真正变化的实体集合；零变化不写 marker、不广播刷新。
3. 保存行动后发送行动变更事件；可见页更新数据，隐藏页标记 dirty，进入时再读。
4. 以数据版本判断缓存有效性，页面只显示缓存或补读已失效数据。不要用单纯 `loaded_once` 代替外部更新检测。

### 2. 后台读仍写操作历史，与知识扫描争写锁（P0，已复现阻塞）

代码：`ui/window.py:920 submit`、`ui/tasks.py:Worker.run`、`storage.py:150 connect`、`knowledge.py:66 scan`。

`persist_result=False` 仅限制结果正文，仍在主线程 `start_task`；Worker 还写“开始/完成”日志和任务状态。每个普通页面读取至少涉及开始记录、开始日志、完成状态、完成日志四次写事务。`connect` 每次新建连接，超时为 15 秒。

与此同时，`KnowledgeIndex.scan` 在一个数据库连接/事务中边读文件边 INSERT、查元数据。首次 DML 后的写锁覆盖后续目录遍历、正文读取与记录处理。扫描虽然在后台，但 UI 的 `start_task` 仍可能等待同一 SQLite 写锁。

改法：

1. 页面读取复用已有 ReadWorker，或提供不落历史的 read 提交入口；备份、恢复、导入、用户编辑等业务操作继续记历史。
2. 在数据库事务外遍历、读取、解析文件；元数据一次批量读出。只在短事务内批量 upsert 变化项及缺失状态。
3. 业务操作的持久化排到后台写入，主线程先生成任务身份和展示忙碌状态；明确失败返回及顺序，保留审计完整性。
4. 无变化扫描不写表；扫描失败与取消保留一致状态。
5. 完成上述结构调整后再评估 WAL。WAL 不能解决两个写入者互相等待，也不能替代短事务。需同时验证快照、加密备份、恢复和数据库所在目录的同步策略。

### 3. 项目读取反复校验全登记表，存在近似平方放大（P1，已计数确认）

代码：`project_workspaces.py:120 registry`、`:213 list_projects`、`:495 document`、`:588 milestones_document`、`:728 project`；`ui/projects.py:1979 refresh`；`ui/workbench.py:415 refresh`。

`registry()` 不只 JSON 解析，还逐项目校验目录、联接与路径边界。项目列表再逐个读取里程碑，每次 `milestones_document → project → registry` 重复完整校验；工作台列出项目后，再逐项目 `document(STATUS)` 也走同一路径。因此项目数量 N 增加时存在 O(N²) 的整表校验成本，并伴随大量 Windows stat/lstat。

项目选择还会在主线程同步 `record_project_use`，涉及登记表读取、校验、锁与 fsync；样例启动中测得约 36～54 ms，早期一次约 97 ms。

改法：

1. 每轮读取创建经过验证的 workspace snapshot，复用项目字典与路径信息；按登记表文件签名失效。
2. 项目列表一次加载 STATUS/里程碑摘要；详情复用同一快照，不在每份文档读取时重新解析整表。
3. 保留每次实际文件访问和写操作所需的路径/联接边界校验；不能为了性能跳过安全检查。
4. 最近使用时间在后台合并写入，选中态立即本地更新，写入前仍比较当前登记内容。
5. 项目页重复进入时保留列表和详情，外部文件签名变化才补读；归档入口修复从每次列表读取中拆出，改为启动检查、生命周期操作后或显式修复。

### 4. 项目详情在 UI 线程解析全部文档并重复重建（P1，长文档已复现）

代码：`ui/projects.py:2157 selection_changed` 及其 `show` 回调；`ui/project_widgets.py:96 overview_snapshot`、`ProjectOverview.set_data`。

当前先用缓存报告执行 show，再后台重读后再次 show；show 重新解析 STATUS/TASKS/HANDOFF、查询关联任务、构建概览控件，更新尚未打开的页签。缓存了原始报告，却没有缓存最终解析结果和渲染签名。

改法：

1. 后台生成纯数据的概览摘要、日志条目、任务集合与资源关联；UI 仅提交短批次更新。
2. 每份文档以文件签名/内容摘要缓存解析结果；报告未变则跳过相应渲染。
3. 初次只渲染当前页签和最近日志；全部历史、笔记、资料预览按打开动作加载。
4. 缓存命中后，后台确认无变化就结束；不要再完整 show 一遍。
5. 长文本控件和大任务列表分批更新；列表持续增长后再按测量决定是否使用 Model/View。

### 5. 知识库未做真正增量索引，预览仍同步（P1/P2）

代码：`knowledge.py:66 scan`、`ui/knowledge.py:1269 refresh`、`:1907 preview_entry`。

扫描的重复 I/O 和写入已实测。每个文件还多次 `_relative`，反复检查祖先联接与 resolve。预览在主线程读文本、解析 Markdown 或解码图片；已有大小限制，但其最坏开销未在真实资料上测量。知识库已有 160 ms 搜索防抖、200 项分页、后台扫描及 loaded_once，切换到知识库并不总会全扫；保留这些已有措施。

改法：文件签名索引缓存；用 scandir/DirEntry 减少重复 stat；同轮复用已经取得的相对路径与属性；缓存正文搜索摘要并只更新变化文件。图片用 QImage 在后台解码缩放，主线程显示；文本预览加版本号、快速切换取消过时结果。保留链接边界、缺失文件和外部引用语义。

### 6. 查询、全局完成回调和后台队列继续放大成本（P2，源码确认）

- `ActionPage.refresh` 一轮分别取 plans、actions、templates、rules 和 today_count，而 `ActionCenter.actions` 内部又读 plans/rules/全部完成记录。今天与搜索视图仍可能先读最多 5,000 项再在 Python 过滤；本轮空任务样例不足以衡量大列表耗时。
- `MainWindow.task_finished` 每个读取完成后都调用 `refresh_common_password`；口令为空时又访问 SecretStore，随后刷新隐藏设置页、检查多个目录。凭据访问已在探针中 mock，真实耗时未验证。
- 数据安全页已在后台收集状态，但每次进入及可见时每个任务开始/完成都会再请求扫描；还会多次枚举归档和逐版本查证据。多版本数据规模未测量。
- 共享线程池为 3 个线程。过时/隐藏页读取与当前页争用；只增加线程数可能扩大磁盘和数据库争用。
- MainWindow 启动预建多个现行页面及旧隐藏页面，存在非必要初始化成本；样例构造显示约 0.63～1.19 秒，不含解释器启动和安装包加载。

改法：行动页一次读取一致快照/聚合计数，按视图下推 SQL 过滤；重复规则与完成记录按必要日期范围取数。口令状态在初始化、设置变更或解锁时刷新，缓存“尚未保存”状态。安全页按备份/校验变化失效，版本懒加载。读任务按页面合并、取消过时请求、当前页优先，保留写操作顺序。最后再做页面懒构造和无引用代码整理。

## 实施顺序与验收

| 阶段 | 交付范围 | 验收重点 |
|---|---|---|
| A：先减少无用工作 | 去掉导航迁移；零变化不广播；可见页刷新/隐藏页 dirty；普通读取不写业务历史 | 相同 12 次切换无重复迁移；无变化回访不写任务表、不触发隐藏页重读；新旧资料增量导入仍正确 |
| B：消除数据库互锁 | 扫描 I/O 移出事务、变化项短事务提交；UI 业务提交异步持久化 | 扫描 200/2,000 文件期间切模块不被数据库写锁阻塞；无变化第二次扫描正文重读与行 upsert 为 0；扫描取消/异常结果一致 |
| C：项目读取与显示 | workspace 快照、解析缓存、详情签名、页签懒渲染、最近使用后台保存 | 14/100 虚构项目下每轮只完整校验一次登记表；350 KB 日志不全量阻塞 UI；外部编辑可正确失效，联接逃逸仍拒绝 |
| D：扩展数据规模与收尾 | 行动查询聚合、预览后台化、安全页缓存、队列优先级、启动懒加载 | 1,000 行行动、10,000 项知识、大图、多版本备份场景分别测量；取消过时请求不覆盖新选择；重复切换不持续增加控件/任务/内存 |

建议验收目标（尚未实现）：

- 同一机器、相同探针配置，热切换 P95 ≤100 ms；单独记录第一屏可用时间与后台稳定时间。
- 10 ms 心跳在常规切换与扫描并行时 P95 ≤50 ms、最大间隔 ≤100 ms；若环境噪声导致失败，保留原始分布并核查具体主线程调用。
- 普通无变化切换对任务记录表写入为 0；隐藏页面不额外读全库。
- 快速切换 100 次，过时读取会取消或合并；最新选择最终正确，无持续队列增长。
- 任务新增/完成/撤销在工作台、计划、项目保持一致；首次/增量导入幂等；外部编辑冲突保护、归档、备份和恢复语义保持。
- 性能评估至少 30 次热切换、3 次独立启动，报告中位数/P95/最大值；性能 profile 与无 profiler 的最终验收分开运行。
